## Problem

The app needs weather for a selected target day and the preceding conditions used by its growth estimate. These are related but different quantities. Recent rain shown to visitors must contain only completed days. The calculation for a future target can include forecast weather between the assessment day and that target. Mixing them would describe predicted rain as rain that has already fallen.

P3 already handles Italian day boundaries and refuses missing forecast data in its historical tests. The application must reuse those safeguards while documenting the difference between a live update's actual retrieval time and a historical test's midnight cutoff.

## Proposed change

Define a stored weather summary keyed by weather cell, fetch, `assessment_date` and `target_date`. Turn hourly answers into daily values when they arrive and store only the daily values. Dates use Europe/Rome and `days_ahead` is zero through seven. Preserve the provider's actual retrieval time, model/source choice, variable units and any known forecast issue time. Do not invent a run publication timestamp where the selected Forecast API does not provide one.

Build two explicit kinds of summary. Visitor recent-rain totals cover the 7, 14 or 21 completed Italian days before the assessment date. The method windows from D18 are rain from 21 to 8 days before the target date, rain of the 7 days before the target date and the weather of the target date. For future targets, the 7-day window may combine completed weather and the saved forecast, with that composition recorded. The target day's weather is a separate dated record.

For example, an assessment on 11 October 2026 has target dates 11 through 18 October. Its visitor recent seven-day rain covers 4 through 10 October. The 21-to-8-day window for 11 October covers 20 September through 3 October, and for 18 October it covers 27 September through 10 October, so that window always uses completed days only. The seven-day window for 18 October covers 11 through 17 October and therefore uses the saved forecast. Later downloads must not rewrite what the estimates of 11 October used.

Aggregate the correct number of hours for 23-hour, 24-hour and 25-hour Italian days. Missing required hours produce incomplete summaries. Preserve nulls per variable so absent optional soil or drying information does not erase valid rain and temperature. Expose frost or drying only when supported by available variables and a documented derivation. Unsupported hail information stays unavailable.

Live fetches may use data fetched during their actual run and must say when that happened. They must not claim to recreate the information available at midnight. Keep the stricter historical-test cutoff unchanged in the research path and document this distinction in `docs/data_formats.md`.

## Acceptance criteria

Add the focused checks in `tests/app/test_weather_summaries.py` and run
`uv run pytest tests/app/test_weather_summaries.py tests/test_weather.py tests/test_forecasts.py`.
Record the worked periods in `docs/weather_summaries.md`.

- [ ] AC1: Hand-calculated fixtures reproduce the October example and every days-ahead value from zero through seven.
- [ ] AC2: Clock-change tests count 23 and 25 hours correctly, and year/leap-year tests preserve the intended target dates.
- [ ] AC3: Deliberately large values after each window boundary never enter its totals. Later weather never replaces a saved forecast that stored estimates already used.
- [ ] AC4: Missing-hour and missing-variable tests distinguish unavailable required summaries from absent optional information and valid zero rain.
- [ ] AC5: Records identify source, units, periods, retrieved time and completed versus forecast contributions. Recent rain is never labelled observed when it is modelled.
- [ ] AC6: The format documentation states the live-run and historical-test time rules. Existing historical cutoff tests still pass.
- [ ] AC7: Unsupported frost, drying or hail information stays absent or explicitly unavailable in fixtures instead of receiving a made-up value.
