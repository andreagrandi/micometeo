## Problem

The owner chose to fetch weather only for areas that visitors look at, instead of downloading all Italy every night. This is D15 in `docs/decisions.md`. The first request for an area on an Italian day fetches the weather of its weather cells and stores it. Every later request that day reads the stored data without calling Open-Meteo.

On-demand fetching adds risks that a nightly job does not have. A visitor waits for the first fetch of the day. Two visitors can ask for the same area at once. One person or a bot panning across Italy can use up the free allowance. Open-Meteo can be slow, down or refuse requests. Each case needs a defined result that never shows invented or shifted data.

## Sources and inputs

- `docs/product_prd.md`, "Coverage, dates and updates" and "Local MVP acceptance", with D15 to D20 in `docs/decisions.md`.
- #44 supplies the square-to-cell mapping, request builder, usage records and limit check. #45 supplies daily values, dated summaries and missing reasons.
- #39 supplies the worker for fetches that outlast a visitor's wait and for the nightly cleanup.
- A run on 11 October 2026 sent 3,726 places in 38 requests of up to 100 places. Each request took about 0.4 seconds. Open-Meteo refused 4 requests as too many after about 2,200 places in 4 minutes, and a retry two minutes later worked.
- [P3 limits](https://github.com/andreagrandi/sporameteo/blob/master/reports/p3_weather.md) include incomplete forecast runs and recent values retained in cache. Retrying must not turn these into silently complete data.

## Proposed change

Store weather per 0.1 degree weather cell and Italian day. When a request needs weather cells that have no weather for today's Italian date, fetch all of them in one Open-Meteo request of up to 100 places through #44, store the daily values through #45, then hand the cells to #48. A new Italian day starts at midnight Europe/Rome, and the first request after it fetches again.

Let only one fetch run for the same cell and day. A second visitor who asks while it runs waits for it and uses its result. Store a fetch only when it is complete and checked: every expected day is present or recorded as a known gap. A refused or interrupted fetch stays pending and is never stored as a gap.

The visitor waits for the fetch up to a documented limit of a few seconds. If the fetch takes longer, answer with what is stored and let the fetch finish in the #39 worker, so the page can ask again.

When Open-Meteo is down or refuses the request, or a limit is reached, return the area's last stored estimates with their real assessment date and fetch time. Never relabel them as today. A cell that has never been fetched shows a translated "not available yet" state with the reason. Before every fetch, ask #44's limit check. Also limit how many new cells one visitor can trigger per minute, so nobody can fetch all Italy.

Each night, a #39 job deletes weather days older than the 21 days the method needs and estimates older than the previous assessment of each area. It makes no Open-Meteo calls. Expose a status command that lists fetches per day, counted calls, refused requests with their messages, pending cells and the last cleanup.

## Deliverables and handoff

- The on-demand fetch-and-store service used by #48 and #49, with one lock per cell and day.
- `docs/weather_updates.md` with the fetch rule, the waiting limit, refusal handling, visitor limits, retention and the nightly cleanup.
- Fetch records with cells, days, counted calls, HTTP status, refusal message and duration.

## Acceptance criteria

Add the focused checks in `tests/app/test_weather_on_demand.py` and run
`uv run pytest tests/app/test_weather_on_demand.py` against local PostGIS
with a fake Open-Meteo server and a fake clock. Record the rules in
`docs/weather_updates.md`.

- [ ] AC1: A first request for an area fetches its missing forest cells in one request and stores them. A second request the same day makes no Open-Meteo call.
- [ ] AC2: Fetch tests cover a new cell with 21 past days, a cell fetched yesterday and a cell last fetched 10 days ago, with the counted calls of each.
- [ ] AC3: Two simultaneous requests for the same cell and day cause exactly one fetch.
- [ ] AC4: Down, slow, refused and over-limit tests return the last stored estimates with their real dates, or "not available yet" for a cell never fetched. No test shows a shifted date or a made-up value.
- [ ] AC5: A visitor-limit test stops one visitor from fetching more than the documented number of new cells per minute.
- [ ] AC6: The first request after midnight Europe/Rome fetches the new day, including on both clock-change days.
- [ ] AC7: Cleanup tests delete only data older than the retention rule and keep everything the current and previous estimates need.
