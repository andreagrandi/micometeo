## Problem

Downloading and summarizing weather is not enough to keep the application current. A daily run can overlap another run, stop after a quota delay, lose a provider response or finish after the laptop wakes. If downstream code reads partially written rows, visitors could see different update dates for adjacent areas or lose a previously usable forecast.

The PRD requires one automatic shared refresh each day and retention of the last completed update. This must work on the local machine before any public server exists.

## Sources and inputs

- `docs/product_prd.md`, "Coverage, dates and updates" and "Local MVP acceptance".
- #39 supplies the database worker, duplicate-execution protection and local scheduling pattern.
- #44 supplies the downloader, cache, persistent quota accounting and national request plan. #45 supplies dated summaries and missing reasons.
- [P3 limits](https://github.com/andreagrandi/micometeo/blob/master/reports/p3_weather.md) include incomplete forecast runs and recent values retained in cache. Retrying must not turn these into silently complete data.

## Proposed change

Add a locally scheduled command that prepares a weather batch for one assessment date. Persist its identifier, start/end times, source configuration, required weather cells and targets, per-cell status and failure reasons. Run it at a documented Europe/Rome time through #39's mechanism. Also provide manual execution for development and missed runs.

Write into a pending batch. Only a verified batch can become the current completed weather batch. "Complete" means every planned cell/date has either validated values or an explicit source-gap result allowed by the documented policy. A transient downloader failure or unfinished quota pause must not masquerade as a permanent geographical gap.

Publish the completed batch through one database change after checking coverage and dates. Keep the previous batch usable if download, validation or publication fails. Protect against an older retried run replacing a newer completed batch. Reuse successful downloads when resuming, while applying #44's rules for incomplete recent responses.

Expose status through a command and structured logs: assessment date, stage, planned/completed/failed cells, counted requests, last completed batch and reason for delay or failure. A running laptop can refresh automatically; a sleeping laptop requires the documented missed-run behavior.

## Deliverables and handoff

- Scheduled and manual weather-update command, batch state and current-batch reference.
- `docs/weather_updates.md` with schedule, completion policy, retry/resume commands, retained history and stale-data behavior.
- A completed batch ID and readiness signal for #48. Weather publication itself must not alter the separately published estimate batch.
- A documented retention policy that preserves the previous usable batch and every weather batch still referenced by retained estimates.

## Acceptance criteria

Add the focused checks in `tests/app/test_weather_updates.py` and run
`uv run pytest tests/app/test_weather_updates.py` against local PostGIS.
Record the schedule and recovery walkthrough in `docs/weather_updates.md`.

- [ ] AC1: A local integration run prepares all planned cells and eight dates and changes the current weather reference only after validation.
- [ ] AC2: Injected download, summary and publication failures preserve the previous batch and leave a useful failure record.
- [ ] AC3: Duplicate, resumed and overlapping job tests avoid duplicate work and prevent an older run replacing a newer one.
- [ ] AC4: Tests distinguish a known source gap from an unfinished request or quota pause. Pending work cannot produce a falsely complete batch.
- [ ] AC5: A retry test reuses completed downloads and refreshes incomplete data according to #44's policy without resetting usage accounting.
- [ ] AC6: The scheduling walkthrough runs locally and records manual recovery after a missed run. It requires no public server.
- [ ] AC7: Retention tests keep weather referenced by the current and previous usable estimate batches. Cleanup cannot break their explanations.
