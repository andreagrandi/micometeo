## Problem

The new Django application and worker need checks that another agent can run before changing them. The repository currently has experiment tests and pre-commit checks, but no application CI workflow. Copying Book Corners' workflow verbatim would also copy its Dokku deployment job, which conflicts with the owner's requirement to finish and accept the MVP locally first.

## Sources and starting points

- Micometeo's `pyproject.toml`, `tests/` and `.pre-commit-config.yaml` define the existing checks and `uv` environment.
- Book Corners' `.github/workflows/ci.yml`, `noxfile.py` and `config/test_settings.py` show PostGIS test services, migration checks and API-schema validation. Reuse the relevant checks, not its hosting secrets or deploy job.
- #38 and #39 provide the application and worker. `docs/product_prd.md`, "Technical starting point", fixes the local-first delivery constraint.

## Proposed change

Add documented commands and GitHub Actions checks for application configuration, migrations, API tests, worker tests and the existing investigation suite. Use a real PostGIS test database for geographic behavior. Use recorded or synthetic provider responses for tests so CI does not download national data, call Open-Meteo or require GBIF and Copernicus credentials.

Keep local and CI commands aligned. Declare required native geographic dependencies and separate database integration setup from fast calculation tests. The workflow must fail on missing migrations, failed tests or configuration errors. Retain secret scanning and file-format hooks.

Do not add an empty frontend build that pretends to check a UI which does not exist yet. #55 will add its real CSS and translation build to the documented checks when it introduces them. Leave a clear handoff for that extension.

## Deliverables

- A checks-only workflow under `.github/workflows/` and any small test configuration it needs.
- A "Checks" section in `docs/local_development.md` with exact commands and network requirements.
- Fixture conventions for data and API tests, including the distinction between local software checks and later real national acceptance in #61.

## Acceptance criteria

Use the documented "Checks" commands in `docs/local_development.md`,
`uv run pytest` and `uv run pre-commit run --all-files`. Inspect the workflow
diff for the publication operations excluded below.

- [ ] AC1: The documented commands run the application, migration, API and worker checks against a fresh local test database.
- [ ] AC2: `uv run pytest` still exercises the existing investigation suite. Tests do not silently skip geographic behavior because PostGIS is missing.
- [ ] AC3: Provider calls are replaced by controlled fixtures in CI. A test run requires no weather, observation or hosting credentials.
- [ ] AC4: The workflow runs the same checks on pull requests and master changes and reports failures through its job status.
- [ ] AC5: Workflow inspection confirms no deployment job, SSH publication, DNS operation, image publication or hosting secret is present.
- [ ] AC6: The delivery report distinguishes checks executed locally from remote CI observed after normal authorized publication. Do not claim a remote pass from a local run.
