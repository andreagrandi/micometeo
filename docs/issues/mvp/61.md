## Problem

The pipeline tickets test their own behavior, but the MVP needs evidence that their real outputs fit together across Italy. P2 measured 504 habitat squares and P6 estimated requests for the home area. Those results cannot be cited as proof that the national product has complete habitat inputs, stays within the free allowance or produces consistent eight-date results when areas are fetched on demand.

This ticket checks the integrated local data flow. It does not measure mushroom prediction accuracy or ask the owner to validate locations in the field.

## Proposed change

Run the documented local setup and the national habitat build with real inputs. Record the code revision, machine, commands, source and build versions, dates, elapsed time, memory and disk.

Create `reports/mvp/local_acceptance.md` with a national-data section. Account for all 20 regions, including Sicily and Sardinia. For each, report squares, forest squares, weather cells with forest and terrain and forest availability. This needs no weather calls. Genuine gaps may remain visible, but an implementation that covers only Tuscany must fail this check.

Then open five real views through the map API, each about 40 to 60 km across: one in the Alps, one in the Apennines, one in the mainland lowlands, one in Sicily and one in Sardinia. Each first view fetches its weather on demand. Keep the real fetches to at most about 300 places in total, and never fetch all Italy to test. Record wait time, counted calls, stored rows and database size. Open each view a second time and confirm it makes no Open-Meteo call. Compare map and detail responses for the same square, date and update, and confirm that source dates and credits reach the API. Include a zoomed-out view, outside-Italy coordinates and a square without forest.

Exercise failures in an isolated local test database with a fake Open-Meteo server: a slow, refused and interrupted fetch, missing required hours, a reached limit, two visitors asking for the same area at once and a failed calculation. Do not damage the real data to stage a test. Verify that an area keeps its last stored estimates with their original dates, including after a clock advance past midnight.

## Deliverables

- Reproducible local integration checks and a national-data section in `reports/mvp/local_acceptance.md`.
- Tables of regional habitat coverage, the five real views, their usage, resource measurements and failure outcomes.
- Exact commands to repeat the checks and a list of unresolved failures. Link fixes to their owning issues rather than treating a report of failure as completion.

## Acceptance criteria

Add integrated data checks in `tests/app/test_local_pipeline.py` and run
`uv run pytest tests/app/test_local_pipeline.py` against local PostGIS.
The real-data runs and resource evidence belong in the
"National data" section of `reports/mvp/local_acceptance.md`.

- [ ] AC1: The report gives squares, forest squares and weather cells with forest for every region, with source versions.
- [ ] AC2: The five real views record wait time, counted calls, HTTP attempts and stored size, using at most about 300 places. A second visit to each makes no Open-Meteo call.
- [ ] AC3: The usage section compares #44's worst case of every forest cell in one day with all the free limits, without reopening pricing research.
- [ ] AC4: Map and detail checks agree on square, date, percentage or status and update, with actual source metadata. A zoomed-out view makes no weather call.
- [ ] AC5: Isolated failure tests keep each area's last stored estimates with their real dates and never shift old forecasts forward or invent a new seventh day.
- [ ] AC6: The documented application and investigation checks pass. Missing national inputs and unchecked behavior remain explicitly listed rather than reported as successful.
- [ ] AC7: The report confirms that these are software and data checks, not validation of the estimated probabilities. No field visits, purchases, VPS or deployment were required.
