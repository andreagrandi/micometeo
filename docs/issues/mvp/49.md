## Problem

The map needs results for the visible area and a selected day, and a way to discover which dates are available. P5 already proved compact GeoJSON responses, but its endpoint generates made-up scores, supports a second species and exposes fourteen assessment dates. Copying that endpoint unchanged would conflict with the selected MVP.

Following D15 and D19 in `docs/decisions.md`, a zoomed-out map shows only where forests are, and estimates appear when the visible map is about 40 to 60 km across or closer. The first request for such a view on an Italian day triggers #46 to fetch the weather of its forest cells. The API must keep missing estimates distinct from zero and must never let a broad view trigger a weather download.

## Sources and reusable code

- [P5 API README](https://github.com/andreagrandi/micometeo/blob/master/apps/api/README.md) defines `/api/v1/info`, `/api/v1/squares`, WGS84 `bbox` and compressed GeoJSON.
- [P5 measurements](https://github.com/andreagrandi/micometeo/blob/master/reports/p5_phone_map.md) measured 7.4 KB compressed for 279 squares and 27 KB for 1,086 squares. Its limit was 4,000 squares and minimum overlay zoom 11. These are starting limits, not national measurements.
- A view 60 by 40 km holds about 9,600 squares. Across Italy about 59 percent of squares have at least 10 percent forest, and in forested mountains nearly all do, so the largest view can exceed P5's cap of 4,000.
- `apps/api/micometeo_api/server.py` and `tests/test_p5_api.py` contain parameter and bounding-box checks worth porting to Django Ninja.
- [Book Corners](https://github.com/andreagrandi/book-corners) files `config/api.py` and `config/api_schemas.py` provide typed API and structured-error patterns. Keep the Micometeo API unauthenticated for all MVP reads.
- #43 supplies the simplified forest layer for zoomed-out views. #46 fetches weather on demand and #48 stores the estimates.

## Proposed change

Implement versioned metadata, forest-layer and map endpoints in the application. Start with the recognizable P5 route names. Define the final schemas in `docs/api.md` and the generated API schema before #56 consumes them.

The metadata response gives today's Italian date, the eight target dates, geographic coverage, the view size from which estimates appear and the square cap. The forest-layer endpoint serves #43's simplified layer as a cached static response with no weather and no estimates.

The map request specifies a WGS84 bounding box and a target date. A view larger than the documented size gets an explicit "zoom in for estimates" answer and triggers no weather fetch. For a smaller view, find its forest squares with the spatial index and their weather cells. Ask #46 for any cell without today's weather, which may fetch it once, then return the stored estimates. Each square in the response carries its whole experimental percentage or unavailable reason, its assessment date and its update ID, because one view can mix areas updated at different times. Squares without forest are marked as having no forest, not as zero.

Measure the response size and drawing time of the largest allowed view on a phone and a desktop, and set the square cap from that measurement. If the largest view is too heavy for a phone, record the numbers and agree a closer starting view with the owner before changing it.

Validate numeric bounds, coordinate order and supported dates. Distinguish malformed input, a view too large for estimates, an outside-coverage view, a valid area with missing estimates, a cell not available yet and an expired update. Return stable error codes and readable messages. #55 and #56 translate the product-facing presentation.

Compress responses. Cache answers by date, view and the update IDs they contain, so a new update never leaves a cached answer claiming old values are current. Do not send full weather histories or explanation text for every polygon.

## Deliverables and handoff

- Typed Django Ninja metadata, forest-layer and map endpoints, geographic queries and compression and cache behavior.
- `docs/api.md` with request examples and small response examples for success, zoom in for estimates, no forest, unavailable data, not available yet, expired update and errors.
- Local measurements of the largest allowed view and the chosen cap, plus API tests runnable with a fake Open-Meteo server.

## Acceptance criteria

Add the focused checks in `tests/app/test_map_api.py` and run
`uv run pytest tests/app/test_map_api.py` against local PostGIS.
Keep response examples and measurement commands in `docs/api.md`.

- [ ] AC1: API contract tests verify square IDs, geometry, percentage or unavailable state, target date, assessment date and update ID against stored fixtures.
- [ ] AC2: Validation tests cover malformed and non-finite bounds, reversed coordinates, unsupported dates and outside-Italy requests.
- [ ] AC3: A view larger than the documented size returns the zoom-in answer and makes no weather fetch. The forest layer contains no estimates.
- [ ] AC4: A first request for a view fetches its missing forest cells once through #46. A second request the same day makes no Open-Meteo call.
- [ ] AC5: No-forest, missing-input, zero-percent and not-available-yet fixtures produce distinct responses described in `docs/api.md`.
- [ ] AC6: Cache tests keep answers apart across dates and updates, including a new update during requests.
- [ ] AC7: The measured largest view and chosen cap are recorded. All reads work without registration and contain no P5 synthetic scores or confidence labels.
