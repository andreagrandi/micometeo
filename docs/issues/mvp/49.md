## Problem

The map needs bounded geographic results for a selected day and a way to discover which dates are available. P5 already proved compact GeoJSON responses, but its endpoint generates made-up scores, supports a second species and exposes fourteen assessment dates. Copying that endpoint unchanged would conflict with the selected MVP.

The product API must serve the real batches from #48, keep missing estimates distinct from zero, and prevent a national view from downloading millions of polygons.

## Sources and reusable code

- [P5 API README](https://github.com/andreagrandi/micometeo/blob/master/apps/api/README.md) defines `/api/v1/info`, `/api/v1/squares`, WGS84 `bbox` and compressed GeoJSON.
- [P5 measurements](https://github.com/andreagrandi/micometeo/blob/master/reports/p5_phone_map.md) measured 7.4 KB compressed for 279 squares and 27 KB for 1,086 squares. Its limit was 4,000 squares and minimum overlay zoom 11. These are starting limits, not national performance measurements.
- `apps/api/micometeo_api/server.py` and `tests/test_p5_api.py` contain parameter and bounding-box checks worth porting to Django Ninja.
- Book Corners' `config/api.py` and `config/api_schemas.py` provide typed API and structured-error patterns. Keep the Micometeo API unauthenticated for all MVP reads.

## Proposed change

Implement versioned metadata and map endpoints in the application. Start with the recognizable P5 route names. Define the final schemas in `docs/api.md` and the generated API schema before #56 consumes them.

The metadata response identifies the published batch, assessment date, produced time, actual available target dates, geographic coverage and map limits. The map request specifies a WGS84 bounding box, target date and result-batch ID. A response includes that identity, whole experimental percentages or explicit unavailable states and stable cell geometry/IDs.

Serve only stored results using a spatial index. Keep the 4,000-cell starting cap unless measurements justify another bounded limit. For a broad view, return an explicit zoom-in state rather than silently truncating cells or returning an empty area that looks like no coverage. Below the overlay zoom the website can still show and search the country. Summary estimates are not required by this ticket.

Validate numeric bounds, coordinate order, supported dates and batch existence. Distinguish malformed input, an outside-coverage view, a valid area with missing estimates, no published batch yet and an expired requested batch. Return stable error codes and readable messages. #55/#56 translate the product-facing presentation.

Compress responses and use cache identities containing the batch, date and geographic request. Publishing a new batch must not make a cache entry claim that old values are current. Retain shared metadata at response level where practical. Do not send full weather histories or explanation text for every polygon.

## Deliverables and handoff

- Typed Django Ninja metadata/map endpoints, geographic queries and compression/cache behavior.
- `docs/api.md` with request examples and complete small response examples for success, unavailable data, broad view, stale batch and errors.
- Local measurements for representative close and broad views, plus API tests runnable without weather-provider access.

## Acceptance criteria

Add the focused checks in `tests/app/test_map_api.py` and run
`uv run pytest tests/app/test_map_api.py` against local PostGIS.
Keep response examples and measurement commands in `docs/api.md`.

- [ ] AC1: API contract tests verify cell IDs, geometry, percentage/unavailable state, target date, assessment date, produced time and batch identity against stored fixtures.
- [ ] AC2: Validation tests cover malformed/non-finite bounds, reversed coordinates, unsupported dates, unknown batches and outside-Italy requests.
- [ ] AC3: A broad-view test enforces the documented cap and returns the explicit zoom-in response without silently dropping matching cells.
- [ ] AC4: Missing-input, zero-percent and no-published-batch fixtures produce distinct responses described in `docs/api.md`.
- [ ] AC5: Compression and cache tests show correct content and separation across dates and batches, including a new publication during requests.
- [ ] AC6: A query check confirms use of the stored spatial data and bounded result retrieval. Requests neither fetch weather nor calculate new estimates.
- [ ] AC7: The API schema and local response measurements are recorded. All reads work without registration and contain no P5 synthetic scores or confidence labels.
