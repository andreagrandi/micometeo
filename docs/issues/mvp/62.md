## Problem

The MVP is not ready for owner acceptance merely because every button has a focused test. The full journey must remain coherent in both languages, on desktop and a real phone, with national data and the chosen design. P5 passed simulated-phone checks yet slowed and froze on an iPhone 15 with Safari after nine successful square requests in 25 seconds.

This ticket checks that integration and the known device risk. A screenshot of the first screen or a successful API log is insufficient evidence for sustained map use.

## Inputs

- The real local pipeline and acceptance report from #61.
- Completed website features #55 to #60 and their focused browser tests.
- `docs/design/decision.md` and its chosen phone/desktop artifacts.
- [P5, On a real phone and Looking for the freeze](https://github.com/andreagrandi/micometeo/blob/master/reports/p5_phone_map.md).
- `docs/product_prd.md`, "Main user journey", "Language and interface quality" and "Local MVP acceptance".

## Proposed check

Run the complete journey as an anonymous visitor in Italian and English. Start from the zoomed-out view that shows only forests, search a place, zoom until estimates appear, note the wait of the first view of that area, select an area, compare today and day seven, read its percentage and facts, switch recent-rain periods, inspect sources, change backgrounds/opacity, save and edit a favorite, reload and reopen it, and hand the destination to navigation. Switch language during the journey and verify that area and date remain selected.

Record the following feature evidence in `reports/mvp/local_acceptance.md`:

| Features | Observable evidence |
|---|---|
| F01, F02, F04, F05 | Real experimental estimates or explained gaps across Italian regions and all eight dates. |
| F11, F12, F18 | Matching explanation inputs, source/update detail, selected-day weather and completed-day rain periods. |
| F13, F14 | Search, permission-based location, map selection, two backgrounds, visibility and opacity. |
| F23, F39 | Persistent local favorites and correct external destination. |
| F70, F76 | Complete use without payment, ads or registration. |
| F72, F75, F81 | Phone/desktop layouts, all IT/EN states and visual agreement with the selected design. |

Exercise slow and failed requests, a slow or refused weather fetch, no estimate, squares without forest, older estimates, denied location, no search results and unavailable favorite storage with controlled fixtures. Keep those simulated failures labelled separately from the real-data journey. Check keyboard access, focus, long translations and readability without relying on color alone.

Use an actual iPhone with Safari for the known failure case, preferably the device used in P5. Record the model, OS/browser, connection and duration. Perform at least 25 map moves over a session of at least five minutes, interleaving zoom, date/background changes, opacity adjustments and opening/closing details. Record progressive slowdown, freezes, failed actions, console/network evidence where available and whether the session stays usable. These are proposed regression-check minimums, not measurements already achieved.

Run from the local machine and reach it from the phone through the Tailscale HTTPS address documented in #38. Use it for the real-phone location-permission check described in #57. Browser emulation may supplement it but cannot be labelled physical-device evidence. If the required phone is unavailable, record the unperformed check and keep acceptance pending.

- [ ] AC1: The report maps all 16 MVP features to observed IT/EN behavior and phone/desktop evidence from the complete journey.
