## Problem

After selecting an area, a visitor should be able to hand its destination to a navigation app. F39 is in the MVP, while route planning, parking suggestions, GPS recording and return-to-car guidance are later features.

The selected destination must survive map movement and detail changes. Sending the map centre, the visitor's current location or swapped latitude/longitude would navigate to the wrong place even though the link opened successfully.

## Sources and inputs

- `docs/product_prd.md`, "Favorites and external navigation".
- #58 supplies the selected destination contract; #57 distinguishes a chosen point from a grid area's representative point.
- `docs/design/decision.md` defines the action's placement and #55 provides translations and focus behavior.

## Proposed change

Add a clearly labelled external-navigation action to the selected-area flow. Use a supported destination-link format with a browser fallback when the native app is unavailable. Choose the simplest provider/platform behavior that works on the tested phones and desktop, document it and check its current link-format documentation during implementation.

Use the exact selected coordinates when the visitor chose a point. For a selected grid area, use the representative destination established by the selection contract and identify that it represents the area. Do not imply it is a parking location, legal entrance, safe trail or known mushroom position.

Validate finite latitude/longitude ranges and construct links from fixed trusted provider templates. Encode labels as data. An editable favorite name must not become HTML or a URL scheme. Open navigation only after the visitor activates the action. The application need not request the visitor's current location to hand over a destination.

When the selected destination is missing or invalid, disable the action and
show a translated explanation. Do not open a navigation page with an empty
destination that defaults to the visitor's own location.

## Deliverables

- Translated navigation control, tested destination-link builder and fallback behavior.
- A short navigation section in `docs/map_behavior.md` with supported devices/browsers and representative-point behavior.
- Manual evidence that the correct destination opens, without starting or recording a journey.

## Acceptance criteria

Add focused checks in `tests/e2e/test_external_navigation.py` and run
`uv run pytest tests/e2e/test_external_navigation.py`. Record the actual
device/browser destination check in `docs/map_behavior.md`.

- [ ] AC1: Link-builder tests verify coordinates and encoding for selected points and grid representatives, including negative longitude and invalid values.
- [ ] AC2: Moving the map after selection does not change the destination, verified by a browser test.
- [ ] AC3: A device/browser check opens the intended coordinates and exercises the browser fallback when a native application is unavailable.
- [ ] AC4: The action and unavailable-destination state work in Italian and English, without registration or SporaMeteo location permission.
- [ ] AC5: User-supplied names cannot inject markup or change the link's scheme/host, verified by unsafe-name fixtures.
- [ ] AC6: The UI describes an external destination handoff and makes no claim about parking, access permission or a safe walking route.
