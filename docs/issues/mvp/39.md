## Problem

Habitat builds, weather fetches that outlast a visitor's wait and the nightly cleanup of old weather and estimates take longer than a page request or must run when no visitor is using the site. The foundation in #38 does not yet provide a worker or a way to start scheduled commands locally.

Book Corners already uses Django's task interface with `django-tasks-db` and a `db_worker` process. Reusing that pattern avoids a separate broker. Its development immediate backend must not accidentally make Micometeo's local web request perform a national job synchronously.

## Sources and starting points

- `docs/product_prd.md`, "Coverage, dates and updates" and "Technical starting point".
- [Book Corners](https://github.com/andreagrandi/book-corners) files `config/settings.py`, `libraries/tasks.py`, `Procfile` and `docker-compose.yml` show the task configuration and worker service.
- Micometeo's `src/micometeo/runner.py` and `context.py` demonstrate run records and error reporting. Preserve their experiment behavior; application jobs need their own state and inputs.

## Proposed change

Configure a database-backed queue and local worker alongside the app and PostGIS. Provide a minimal command-to-task pattern that #46 can use for weather fetches that outlast a visitor's wait and for the nightly cleanup, and that the habitat builds can use for long imports. The task should receive identifiers for persisted inputs, not large geographic datasets serialized into the queue.

Document a local scheduling mechanism that can invoke a command once a day. A local operating-system scheduler or a small documented scheduler process is sufficient. Explain what happens while the laptop is asleep and how to run a missed job manually after waking it. Do not promise jobs run while the computer is off.

Make waiting, running, completed and failed jobs inspectable through a command or existing administration facility. Capture start/end times and a useful failure reason. Provide controlled retries and protection against duplicate or overlapping execution of the same logical run. This ticket establishes the mechanism; #46 owns the weather fetching and cleanup rules.

## Deliverables and handoff

- Local worker configuration and a small representative queued job that performs no network downloads.
- Scheduling, status, retry and restart commands in `docs/local_development.md`.
- An integration test using the database worker, separate from faster tests that execute tasks immediately.
- A documented convention for logical job keys, input IDs and failure status for #46.

## Acceptance criteria

Add the focused checks in `tests/app/test_background_jobs.py` and run
`uv run pytest tests/app/test_background_jobs.py` with the local database
worker. Record the schedule walkthrough in `docs/local_development.md`.

- [ ] AC1: The worker walkthrough enqueues the representative job, returns control to the caller and observes its persisted completion in a separate worker.
- [ ] AC2: An integration test records a forced job failure and a successful retry with the original failure still inspectable.
- [ ] AC3: A duplicate-execution test proves two starts of the same logical job cannot perform its protected work concurrently.
- [ ] AC4: A worker-restart test retains queued work, does not rerun a completed job and accounts for interrupted work without silently reporting success. A failed job leaves the worker able to process a subsequent job.
- [ ] AC5: The schedule walkthrough states the Europe/Rome schedule, missed-run behavior and manual invocation. It requires no VPS or always-on public service.
- [ ] AC6: A request-path test confirms that queuing the representative job does not execute its work inside the HTTP request.
