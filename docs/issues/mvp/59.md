## Problem

Visitors need to keep useful areas and return to them without registering. F23 is selected for the MVP, while accounts and cross-device synchronization are deferred. Saving favorites to a user table or silently submitting locations would violate that decision.

Browser storage can be unavailable, full or malformed. The app must explain those failures rather than telling a visitor that a place was saved when it was not.

## Sources and inputs

- `docs/product_prd.md`, "Favorites and external navigation", defines adding, naming, optional colors, reopening, renaming and removing browser-local favorites.
- `reports/Porcini app feature comparison.md`, F23, records the selected feature and browser-local refinement.
- #58 provides the selected point or grid area and #55 supplies the design and translations. Follow `docs/design/decision.md` for the list and editing controls.

## Proposed change

Store a small versioned favorite record in the current browser. It includes a stable local ID, point or grid-area kind, coordinates, cell ID when applicable, an editable name and optional color. Save the location, not a frozen prediction. Reopening a favorite selects that destination and obtains the current supported estimate through the existing map/detail flow.

Support add, list, open, rename, recolor and remove. Define duplicate behavior explicitly, preferably selecting the existing favorite for the same saved area rather than silently creating repeated entries. Allow a useful default name when no place name is available. Validate stored coordinates and fields before using them. Treat user names as text, never HTML.

Show that favorites stay in this browser, do not synchronize and may disappear if browser data is cleared. Storage writes must succeed before showing saved state. Handle disabled storage, quota failure and malformed saved records without breaking the map or discarding unrelated valid entries silently. Document the storage version and how a future version will be recognized.

Keep favorites available when a location currently has no estimate. The saved place remains valid even if a weather update fails. If a saved point is outside supported coverage or an old cell ID no longer resolves, show its location and a clear state rather than jumping to another place.

## Deliverables

- Browser persistence module, selected-area save action and favorite list/edit/remove flows.
- Italian and English storage/privacy/failure messages following the chosen design.
- `docs/favorites.md` with the stored format, duplicate rule and failure behavior.

## Acceptance criteria

Add browser checks in `tests/e2e/test_favorites.py` and run
`uv run pytest tests/e2e/test_favorites.py`. Record the storage-format and
network-inspection results in `docs/favorites.md`.

- [ ] AC1: Browser tests add a point and a grid area, reload the page, reopen them and preserve their names and optional colors.
- [ ] AC2: Rename, recolor, duplicate and remove tests follow the documented behavior and persist after reload.
- [ ] AC3: Reopening a favorite uses the current supported result rather than displaying a saved percentage or changing coordinates to the map centre.
- [ ] AC4: Disabled/full storage and malformed-record tests show translated failures, retain usable entries and keep the map working.
- [ ] AC5: Names containing HTML-like text render as text. Invalid saved coordinates cannot trigger unsafe links or arbitrary requests.
- [ ] AC6: A network check confirms favorite contents are not uploaded or used for prediction training. The browser-only persistence notice appears in both languages.
- [ ] AC7: A saved area with missing weather remains in the list and opens with the normal unavailable-result state.
