## Problem

The existing map demonstrates serving synthetic scores. It does not implement the agreed product journey, the two languages or the owner-selected design. P5 also froze after repeated movement on an iPhone 15 in Safari even though every API request succeeded. Merely replacing its scores would not produce an acceptable MVP.

Visitors need to find an Italian place, choose today or a future day, understand an experimental percentage, inspect its weather and sources, save it privately and open navigation. Those actions must work together on phone and desktop without accounts or payment.

## Goal

Implement the design chosen in #54 as a complete bilingual map website. Curated appearance, readable states and touch usability are part of delivery, not optional work after launch.

## Evidence and starting points

- `docs/product_prd.md` defines the 16 MVP features. Relevant behavior is repeated in the child tickets so an agent can implement them without reconstructing the interview.
- `docs/design/decision.md`, produced by #54, will define the actual visual direction. Do not choose production layouts before it exists.
- [P5 report](https://github.com/andreagrandi/micometeo/blob/master/reports/p5_phone_map.md) gives the API sizes, zoom limits, touch findings and unresolved real-phone freeze.
- [P6 map assessment](https://github.com/andreagrandi/micometeo/blob/master/reports/p6_cost_licence_portability.md) distinguishes OpenStreetMap data from permission to use its standard tile server.
- Reuse the [Book Corners](https://github.com/andreagrandi/book-corners) Django templates, HTMX, Tailwind/daisyUI and Leaflet patterns. Keep map state in one controlled client component. Replacing that component during unrelated partial-page updates must not accumulate maps or event listeners.

| #60 | Hand the selected destination to an external navigation app. |

The update ID, target date and selected square must remain consistent across map and details. The first view of an area each day can wait briefly while its weather is fetched, and needs a readable loading state. Changing dates or places must not let a slower old response replace the latest selection. Missing data, older updates and provider failures need readable states in both languages.

## Acceptance criteria

- [ ] AC1: The child browser checks cover the complete journey in Italian and English, without registration, advertising or subscriptions.
- [ ] AC2: The phone and desktop views match #54's selected design and recorded adjustments. Visual review is recorded against that artifact.
- [ ] AC3: Map and detail tests reject outdated responses and keep selection, dates and language consistent through repeated interactions.
- [ ] AC4: Source credits remain readable, missing results differ from zero and experimental status appears in the legend and details.
- [ ] AC5: The sustained physical-phone check in #62 passes before the whole MVP is accepted. Emulation alone does not clear the known Safari problem.
