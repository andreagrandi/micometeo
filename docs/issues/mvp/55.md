## Problem

The selected design needs a real application layout that later map and detail tickets can extend. The P5 page is a separate demonstration and has no complete Italian/English journey. Using default components without the chosen typography, spacing and states would miss F81 even if the controls technically work.

This is the first production UI ticket. It must wait for the owner's design decision in #54. The application foundation alone does not authorize choosing a layout.

## Sources and starting points

- `docs/design/decision.md` and selected artifacts from #54 are the visual authority.
- `docs/product_prd.md`, "Language and interface quality", requires the same complete journey on phone and desktop and translated errors and explanations.
- Book Corners' `templates/base.html`, `config/settings.py`, `assets/css/input.css` and `package.json` provide Django templates, translation configuration and Tailwind/daisyUI build patterns.
- #38 supplies the app. #40 defines checks that this ticket must extend for real CSS and translation assets once they exist.

## Proposed change

Implement the chosen responsive shell with the map area, control regions, detail-panel container and shared loading, empty, unavailable and error components. Follow the selected design's type scale, spacing, colors, layout and interaction rules. Do not substitute a generic dashboard or a third mockup.

Use Django templates and HTMX where useful, with a defined persistent client component for the map. Identify which elements can be replaced by partial updates and which must preserve their state. Use Leaflet as the map starting point in later work unless a concrete need for another renderer is documented.

Support Italian and English through Django's translation pattern and a visible switch. Initial language may follow the browser. Persist an explicit user selection locally. Changing language must preserve area, target date, map view and open product state once those integrations are added. Establish that state contract now with fixtures. Forecast dates always use Europe/Rome; language changes only presentation.

Translate shared controls and states, including browser-generated failure explanations represented by the application. Build the real CSS and translation catalogs through the normal documented checks. Keep source names and user-entered favorite names separate from translated interface text.
