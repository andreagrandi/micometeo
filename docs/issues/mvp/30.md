## Problem

Micometeo currently contains a Python experiment runner, data-processing modules and a separate demonstration API and map. These proved parts of the system could work, but they do not provide the database, application configuration or background processes needed by the agreed product. Building each next ticket around those independent experiments would leave incompatible commands and duplicated configuration.

The owner selected a free Italian and English website covering all Italy, with experimental porcini growth percentages for today and the next seven days. All development and acceptance must run locally. A public server is not a prerequisite for any MVP ticket.

## Goal

Provide one local Django application, a PostGIS database for geographic records and a database-backed worker. Preserve the existing investigation commands and results. Use Book Corners as the concrete implementation reference.

## Evidence and starting points

- `docs/product_prd.md`, sections "Technical starting point" and "Local MVP acceptance", defines the product decisions. Epic 1's regional scope does not limit this application.
- [Current Python project](https://github.com/andreagrandi/micometeo/blob/master/pyproject.toml) uses `uv`, Python 3.12 or newer and `src/micometeo`. Retain its package and experiment entry point.
- [P5 report](https://github.com/andreagrandi/micometeo/blob/master/reports/p5_phone_map.md) describes a standard-library API and synthetic results. Its API contracts and measurements are references, not the production architecture.
- In [Book Corners](https://github.com/andreagrandi/book-corners), inspect `config/settings.py`, `config/api.py`, `docker-compose.yml`, `Procfile`, `noxfile.py` and `.github/workflows/ci.yml`. Reuse their Django Ninja, PostGIS and database task patterns. Its workflow also deploys to Dokku, which must be excluded here.

## Scope and child outcomes

| Child | Outcome | Handoff |
|---|---|---|
| #38 | Start Django, its API and PostGIS with documented local commands. | Application layout, settings, migrations and a health endpoint for all later work. |
| #39 | Run queued work and a local schedule with recoverable job status. | A command and worker pattern for habitat builds and #46's long fetches and nightly cleanup. |
| #40 | Run application and experiment checks locally and in CI. | Repeatable checks without provider credentials or deployment secrets. |

Use one database and the existing Python dependency workflow. Do not introduce a separate JavaScript application, Redis or another queue merely for setup. Keep geographic and calculation code reusable outside HTTP requests. Long downloads and national calculations belong in commands or jobs.

## Acceptance criteria

- [ ] AC1: The setup walkthrough in `docs/local_development.md` starts the application and PostGIS from a clean checkout and runs migrations without a domain or public server.
- [ ] AC2: The worker walkthrough queues a job, observes completion and records a failure and retry without corrupting job state.
- [ ] AC3: The commands added by #40 run both application checks and the existing experiment tests. CI contains no deployment action.
- [ ] AC4: The child documentation identifies reused Book Corners files and explains any necessary departure. Existing `uv run micometeo` commands still resolve.

## Boundaries

UI design belongs to #34 and production UI starts only after #54. This epic does not implement weather, prediction logic, user accounts, payments or hosting. Never buy services or deploy to a VPS. The complete local product must receive the owner's acceptance in #63 first.
