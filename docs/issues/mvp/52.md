## Problem

The owner explicitly wants to evaluate a mockup made by Google Stitch before UI work. A prompt alone is not that mockup, and an agent-made image cannot be substituted while retaining the Stitch label. The output must show enough of the selected MVP to compare with the independent design from #53.

## Inputs

- `docs/design/brief.md`, `stitch_prompt.md` and shared sample content from #51.
- `docs/product_prd.md`, "Mockup epic requirements" and "Language and interface quality".
- [P5 phone report](https://github.com/andreagrandi/micometeo/blob/master/reports/p5_phone_map.md) for readable map controls and detail-panel constraints.

## Proposed change

Use the prepared prompt in Google Stitch and obtain an actual generated design. If access requires the owner's signed-in session or a manual export, identify that concrete step during execution. Keep the issue open until the Stitch result is available. No paid subscription is authorized.

Inspect the generated design against #51's feature/state checklist. Iterate the prompt where Stitch omits selected functionality, uses unreadable phone controls or introduces deferred features. Save the prompt revisions and identify which output each revision produced. The deliverable must remain a Stitch design even if small presentation annotations are added later.

Cover the same phone and desktop journey as #53. At minimum, retain views for the main map, selected-area percentage and weather, future date selection, background/opacity controls, favorites and a missing-data/error state. Include Italian and English content that exposes text-length differences. Show how a phone user can return from details to the map and reach the other controls.

## Deliverables

- `docs/design/stitch/README.md` with the generation date, prompt used, project/export reference, iteration record and how to inspect the result.
- The export or stable accessible artifact, plus locally inspectable representations of required screens. Save temporary browser screenshots under `/tmp/` when collecting evidence.
- A completed copy of #51's checklist, noting any state represented by an annotation rather than an interactive screen.
- A short account of design choices and remaining limitations for comparison in #54. Do not claim static artwork proves working interactions.
