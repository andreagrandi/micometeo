## Problem

The calculation in #47 can evaluate one set of inputs. The app needs a repeatable national result for every supported area and all eight target dates. Computing inside map requests would couple response time to national work. Reading a partially updated table could also show one percentage on the map and another in the selected-area panel.

The PRD requires consistent publication and preservation of the last completed update. An older forecast keeps its original dates when a refresh fails. It must never be shifted forward to make it look current.

## Sources and inputs

- `docs/product_prd.md`, "Coverage, dates and updates".
- #47 provides the calculation, method version and contributing facts. #46 provides a completed weather batch. #41 to #43 provide the national grid and versioned habitat inputs.
- [P6, Daily work](https://github.com/andreagrandi/micometeo/blob/master/reports/p6_cost_licence_portability.md) measured fast scoring for the pilot, but used synthetic weather. Measure the real national job rather than reusing that number as a guarantee.
- [P5](https://github.com/andreagrandi/micometeo/blob/master/reports/p5_phone_map.md) demonstrated the value of serving precomputed results.

## Proposed change

Add a local command/job that binds one complete weather batch, one habitat build and one method version, then evaluates the national grid for assessment day through day seven. Persist the result-batch ID, source IDs, actual calculation time and eight target dates. Store percentage or explicit unavailable status for each expected cell/date, together with the explanation inputs needed by #50.

Also store a summary for each 10 km block and target date, so a zoomed-out map can show the whole country. Blocks use the same EPSG:3035 grid with IDs like `10km_E4320000_N2340000`, so each block holds exactly 20 by 20 squares. A block's value is the highest whole percentage among its squares, with the number of squares that have an estimate and the number that do not. A block where no square has an estimate is unavailable, not zero. Blocks belong to the same result batch as their squares and pass the same checks before publication. The block value describes the best 500 m area inside it, not a chance for the whole block.

Process in chunks and retain progress so a failed chunk can resume. A completed batch accounts for every expected grid cell and target date. Known missing inputs may produce explicit unavailable rows; skipped processing and unknown failures do not count as completion. Detect duplicate IDs, missing targets, inconsistent source versions and invalid results before publication.

Use one atomic current-result reference after validation. A calculation failure or interrupted database write leaves the previous published result usable. A delayed older run cannot replace a newer assessment. Keep the data needed to answer requests pinned to the previous batch long enough for an in-progress page to finish, and document the retention window. Retain referenced weather and habitat metadata as well.

The APIs should be able to select a particular published batch. A page that loaded map data from one batch must either receive details from that batch or an explicit expired-batch response directing it to refresh. It must never receive another batch silently.

## Deliverables and handoff

- National calculation command, resumable run records, stored estimates and atomic publication.
- `docs/estimate_updates.md` defining batch identity, completeness, retry, retention and rollback-to-previous behavior.
- A local run report with actual cell/date counts, unavailable reasons, duration, peak memory and disk size.
- Queryable results and metadata consumed by #49 and #50. No API request downloads weather or runs the national calculation.

## Acceptance criteria

Add the focused checks in `tests/app/test_estimate_updates.py` and run
`uv run pytest tests/app/test_estimate_updates.py` against local PostGIS.
Record national execution and retention checks in `docs/estimate_updates.md`.

- [ ] AC1: A fixture run produces exactly eight targets for every planned cell, with either a valid estimate or a documented unavailable reason, and a 10 km block summary per date that matches the highest estimate and counts of its squares.
- [ ] AC2: Validation tests reject missing rows, duplicates, mixed input versions and non-finite percentages before the current reference changes.
- [ ] AC3: Failure tests at calculation, storage and publication preserve the previously published batch and its explanations.
- [ ] AC4: Retry and overlap tests avoid duplicate rows, reproduce the same estimates for unchanged inputs and prevent an older assessment replacing a newer one.
- [ ] AC5: Snapshot tests read map and detail data from the same requested batch while a new one is published. Expired batches produce an explicit result.
- [ ] AC6: A clock-advance test preserves the original target dates and produced time of stale results. It does not invent a new seventh forecast day.
- [ ] AC7: The local run report records national counts and resources using real available inputs. Retention checks preserve every source record needed by retained estimates.
