## Problem

The calculation in #47 can evaluate one set of inputs. The app needs stored estimates for every forest square of an area and all eight target dates as soon as that area's weather has been fetched by #46. Reading a half-written result could show one percentage on the map and another in the selected-area panel.

The PRD requires consistent results and preservation of the last completed estimates. An older forecast keeps its original dates when a fetch fails. It must never be shifted forward to make it look current.

## Sources and inputs

- `docs/product_prd.md`, "Coverage, dates and updates", with D15, D17 and D20 in `docs/decisions.md`.
- #47 provides the calculation, method version and contributing facts. #46 provides stored weather per weather cell and day. #41 to #43 provide the grid, terrain and forest squares.
- A measurement on 11 October 2026 calculated a placeholder value for all 713,173 forest squares and eight dates in 0.02 seconds. The real formula from #47 is still to be measured.
- [P5](https://github.com/andreagrandi/micometeo/blob/master/reports/p5_phone_map.md) demonstrated the value of serving stored results.

## Proposed change

Add a service that, for a set of freshly fetched weather cells, evaluates every forest square in them for the assessment day through day seven. Only squares with at least 10 percent forest get estimates, following D17. Other squares are stored once as having no forest and are never calculated.

Store one row per forest square holding all eight dates, following D20. Each row records the assessment date, an update ID, the weather fetch, habitat build and method version it used, and the calculation time. Each date holds a whole percentage or an explicit unavailable reason. Store the explanation inputs that #50 needs once per weather cell and once per square, not once per date.

Write an area's new estimates in one database change after checking them: one row for every forest square of the cell, eight dates each, no duplicates, one set of input versions and finite percentages. A failed calculation or interrupted write leaves the area's previous estimates in place. A delayed older calculation cannot replace a newer assessment.

Keep only the current and the previous assessment of each area, so a page that loaded the previous one can still open its details. A detail request for an update that has since been deleted gets an explicit expired response asking the page to refresh. It never receives a different update silently. The nightly cleanup from #46 deletes anything older.

## Deliverables and handoff

- Calculation service called after each fetch, stored estimates and the one-change write.
- `docs/estimate_updates.md` defining the update ID, row layout, checks, retention and the expired response.
- Measured time and size for calculating and storing one weather cell and all Italy, with the database size after the current and previous assessment of every forest square.
- Stored results and metadata consumed by #49 and #50.

## Acceptance criteria

Add the focused checks in `tests/app/test_estimate_updates.py` and run
`uv run pytest tests/app/test_estimate_updates.py` against local PostGIS.
Record the measurements and retention checks in `docs/estimate_updates.md`.

- [ ] AC1: A fixture calculation produces one row per forest square of the cell with exactly eight dates, each a valid estimate or a documented unavailable reason. Squares without forest get no estimate.
- [ ] AC2: Check tests reject missing rows, duplicates, mixed input versions and non-finite percentages before anything is written.
- [ ] AC3: Failure tests at calculation and storage keep the area's previous estimates and their explanations.
- [ ] AC4: Repeat tests reproduce the same estimates for unchanged inputs, and an older assessment never replaces a newer one.
- [ ] AC5: Map and detail reads for the same square and update agree. A deleted update produces the explicit expired response.
- [ ] AC6: A clock-advance test keeps the original target dates and calculation time of old estimates. It never invents a new seventh forecast day.
- [ ] AC7: The measurements record calculation time per cell, and the database size for all Italy stays near the estimated 100 MB for estimates.
