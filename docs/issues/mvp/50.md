## Problem

A map percentage alone does not satisfy F11, F12 and F18. Visitors need the actual weather and habitat facts behind that number, their source dates and limitations. P5 repeats generic synthetic source names and assigns reliability from days ahead. Those fields cannot become the product's explanation.

The selected-area response must come from the same stored update as the map square. Looking up the newest weather while displaying an older percentage would give an explanation for a different calculation.

## Sources and inputs

- `docs/product_prd.md`, "Percentage meaning and calculation" and "Explanations and weather".
- #47 defines contributing facts; #45 defines selected-day weather and completed-day rain totals; #48 binds them to the update of each square.
- [P2](https://github.com/andreagrandi/sporameteo/blob/master/reports/p2_habitat.md) explains coarse or old habitat inputs. [P3](https://github.com/andreagrandi/sporameteo/blob/master/reports/p3_weather.md) explains modelled recent weather and weaker longer-range forecasts.
- [P6 credits](https://github.com/andreagrandi/sporameteo/blob/master/reports/p6_cost_licence_portability.md) supplies required source attribution. Keep factual input quality distinct from unmeasured prediction accuracy.

## Proposed change

Add a typed area-detail endpoint addressed by square ID, target date and update ID. Keep those identities consistent with #49's map contract. Use the stored calculation's references rather than recomputing against the latest inputs. Never fetch weather from this endpoint. Share format conventions through `docs/api.md`; this ticket can proceed alongside #49 from #48's storage contract.

Return the following groups of information in a documented schema:

| Group | Required information |
|---|---|
| Selection | Square ID, geometry or bounds, representative coordinates, target date, assessment date, days ahead and update ID. |
| Estimate | Whole experimental percentage or unavailable status, produced time, method version and unvalidated-status explanation. |
| Contributing facts | The actual input value, units, period/source, rule or method role and structured explanation key from #47. |
| Weather | Selected-day weather and recent rain for 7, 14 and 21 completed days, with explicit period boundaries and completed/forecast distinction. |
| Sources and gaps | Source names and links, dataset/survey dates, retrieval times, supported geographic detail, missing reasons and attribution text. |

Optional drying, frost or hail information appears only when the stored source and derivation support it. Missing optional fields must not invalidate an otherwise available percentage. Do not invent a numeric confidence interval or label days zero to two as high accuracy. Explain that 500 m areas can share weather covering several kilometres.

Use structured explanation and error keys with values so #58 can translate complete sentences in Italian and English. Source proper names and licence text remain intact where needed. Unknown squares, squares without forest, absent results and expired updates must be distinguishable.

## Deliverables and handoff

- Area-detail endpoint and typed schema with examples in `docs/api.md`.
- Fixed response fixtures for an available result, required-input gap, old update, absent optional weather and coarse/old source detail.
- A consistent selected destination for #58 to pass to favorites and navigation without confusing map centre with selected coordinates.

## Acceptance criteria

Add the focused checks in `tests/app/test_area_api.py` and run
`uv run pytest tests/app/test_area_api.py` against local PostGIS.
Use `docs/api.md` as the checked schema and example reference.

- [ ] AC1: API tests compare map and detail fixtures for the same square, date and update and obtain the same percentage or unavailable result.
- [ ] AC2: A new update of the area does not change a detail response for the retained previous update. A deleted update produces a documented expired error.
- [ ] AC3: Each contributing fact matches the stored calculation input and version. A test changes an input and verifies the corresponding fact changes.
- [ ] AC4: Weather fixtures verify all three recent-rain periods and selected-day dates without folding future rain into completed-day totals.
- [ ] AC5: Missing required and optional values, zero rain and unavailable estimates remain distinct and machine-readable.
- [ ] AC6: Responses preserve source dates, real input detail and applicable credits. They contain no invented prediction-confidence numbers or P5 reliability labels.
- [ ] AC7: Error and explanation keys support both languages without putting untranslated product prose into structured input values.
