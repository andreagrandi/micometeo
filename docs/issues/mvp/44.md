## Problem

Weather must be fetched once per weather cell and day, and reused by every visitor and 500 m square in that cell. Following D15 to D17 in `docs/decisions.md`, the app fetches weather on demand, uses cells of 0.1 degrees, about 11 by 8 km, and fetches only cells that contain forest squares. Italy has 3,726 such cells. Fetching all of them in one day counts about 3,726 calls when each request covers at most 14 days, or about 7,700 when every cell needs its first 29 days.

The existing experimental client is a useful starting point, but `forecast_hourly` requests `forecast_days=1`. Its `_request` counter increments once for an entire retry sequence, `_fetch` counts quota before that sequence, and the cache key does not express every request parameter. P3 also recorded incomplete recent weather persisting in the cache. These are explicit implementation gaps for this ticket.

A retry two minutes later worked.

## Proposed change

Map every forest square to its 0.1 degree weather cell and store that mapping. A weather cell is fetched only if it contains at least one forest square. Request each cell at its centre and record that point. Explain the temperature-elevation policy, because Open-Meteo corrects temperature for the altitude of the requested point; #47 must not correct it a second time.

Use the Forecast API for recent weather and future days. A cell with no stored weather asks for the 21 previous days, today and the next 7 days. A cell with stored weather asks only for the days it is missing, plus a short overlap of recent past days whose values can still change, plus today and the next 7 days. Keep that request within 14 days and ten variables, so it counts one call per place. Send up to 100 places in one request and count each place.

Use request identity that includes endpoint, coordinates, model choice, variables, date coverage, time-zone handling and relevant provider options. Count every network attempt, including retries and refused requests. Stored data that is reused consumes no calls.

Persist usage across process restarts. Stay below 600 counted calls a minute, 5,000 an hour and 10,000 a day, with a margin. On a 429 answer, record the full message, wait and retry later, and leave the request marked as pending, never as a gap in the data. Provide the limit check that #46 calls before each fetch, so no visitor can push usage over a limit.
